# Zero-Touch Federated Learning — Label-Flip Poisoning vs an RL-Trained Defender LLM

A research testbed where a **detection-adaptive label-flipping attack** runs
against a **defender LLM** that is reinforcement-trained on-line with verifiable
rewards, in a federated-learning setting on MNIST.

## Overview

Two phases:

1. **Phase 1 (`training_rounds`):** All clients train honestly via FedAvg. The
   global model, each client's weights, and the baseline accuracy are
   checkpointed.
2. **Phase 2 (`simulation_rounds`):** A fixed set of insider clients
   (`attack.poison_client_ids`, default `[0]`) trains each round on **its own data
   with a share of the labels flipped**, and the defender LLM tries to spot them.

### The attack — label flipping on a ladder

The flip is **symmetric**: `y → 9 − y`, so `0↔9, 1↔8, … 4↔5`. The standard
label-flipping attack in the FL-poisoning literature (Fang et al., USENIX Security
2020; Tolpegin et al., ESORICS 2020).

Nothing edits the weights. A poisoned client runs the *same* local training on the
*same* examples for the *same* epochs at the *same* learning rate as it would have
honestly — only the labels differ. Whatever update comes out is a genuine SGD
trajectory, so it sits inside the honest update distribution by construction.

**How many labels get flipped is driven by the defender:**

```
start:  flip 100% of the poisoned client's data for this round
CAUGHT      -> step down one notch (10%):  100% -> 90% -> 80% -> ...
NOT CAUGHT  -> HOLD. Send the same level again, unchanged.
CAUGHT at the floor (50%) -> RESET to 100% and descend again.
```

On a client holding 1000 examples per round that is exactly 1000, 900, 800, 700,
600, 500 — then back to 1000. The attack probes for the largest poison the
defender still misses, holds whatever is working, and backs off only when caught.

- **The floor exists** because below about half the client's data the honest
  gradient dominates its own update: the round stops being an attack and becomes
  noise, so neither "caught" nor "missed" carries information.
- **The reset exists** so the run does not park at the floor forever, training the
  defender against one static, barely-detectable setting for the rest of its life.

So the curriculum the defender faces is generated by **its own failures**. That is
something a fixed poison rate cannot do: a fixed rate is either always easy (and
the defender stops learning after a few rounds) or always impossible (and it never
gets a gradient).

> **Why the poison is in the DATA, not the weights.** This project previously used
> an attacker LLM emitting weight-space operator plans (scale, sign_flip, mask,
> noise…). That was removed. A weight-space edit is a post-hoc transform of a
> vector the client already computed, so its magnitude is a free parameter the
> attacker can dial to whatever a detector tolerates, and the result need not
> resemble anything a real client would send — which makes "did the detector catch
> it" a question about outlier arithmetic rather than about poisoning. A label flip
> has exactly one knob and always produces a real gradient of a real objective.

### The defender — the only learner

Input: per-client, per-layer statistical feature vectors of each client's weight
delta. Output: a direct **benign/malicious classification per client**, after which
the server FedAvg-aggregates the clients it did not flag.

Because we know the ground-truth poisoned set, it gets an exact **verifiable
reward** (a confidence-weighted soft F1) and is trained on-line with **GRPO**. The
ground truth is a *training signal only* — it never enters the prompt.

Its verdicts on the committed round then drive the attack ladder, so the two
co-adapt without either seeing the other's internals.

The alternative (`defense.mode: algorithmic`) swaps the LLM for a published
algorithm — see [Defense modes](#defense-modes). That leaves nothing to train, so
it is for `--dry-run` / `--baseline` / the benchmark.

### Measuring the attack

Damage is scored against the round's **clean counterfactual** — the accuracy the
aggregate reaches with the *same clients* trained on the *same data* with their
*real* labels. The two branches differ by nothing but the labels, so the drop
isolates the attack exactly. It is reported as `attack_effectiveness`
(1.0 = achieved `attack.goal.target_accuracy_drop`); nothing is trained on it,
because the attack has no policy.

## Defense modes

`configs/base.yaml` ships with **`defense.mode: llm`** — the trainable defender.
Setting `defense.mode: algorithmic` swaps in the published algorithms already
implemented for the benchmark, **one per round**:

| Algorithm | What it does |
|---|---|
| `fltrust` | Cosine trust vs a clean root update, norm-rescaled, trust-weighted (NDSS'21) |
| `defl` | Per-layer FGNV + MOUD-Vote + CLP gating with Beta trust (AAAI-23) |
| `dnc` | Spectral (top-singular-direction) outlier filter (NDSS'21) |
| `multikrum` | Distance-based selection of the `n - f` most central updates (NeurIPS'17) |

Details that matter:

- **`python main.py` refuses to train in this mode**, and says so: the attack is a
  fixed schedule and the algorithms are not policies, so there is nothing to
  optimize. Use it with `--dry-run`, `--baseline`, or `benchmark.run_benchmark` —
  where it measures those algorithms against the same label-flip ladder.
- **One algorithm defends the whole round.** It is fixed in `env.begin_round()` and
  used for the round's clean counterfactual and the commit, so the numbers stay
  comparable within a round.
- **The algorithm also produces the aggregate.** FLTrust re-weights and rescales,
  DeFL Beta-weights and CLP-gates; reducing them to a drop-list for FedAvg would
  throw the defense away. So `env.defend()` returns the verdicts *and* the new
  global, and the env commits that state (`env.commit_state`).
- **Scoring never advances the defense's memory.** DeFL's Beta counts and `S(t-1)`
  (and DnC's subsampling RNG) are snapshotted and rolled back for every uncommitted
  call.
- Every round log records which defense faced it
  (`attack_metadata.defense` in `logs/round_data/rounds.jsonl`). Compare rounds
  **within** a defense — accuracy drops are not comparable across them.

## Training curriculum (algorithmic defense only)

Under `defense.mode: algorithmic`, `curriculum:` replaces the random per-round
algorithm draw with a deterministic sweep:

```
fltrust   × 10 rounds → defl × 10 → dnc × 10 → multikrum × 10 → …repeat
```

Every algorithm gets exactly the same number of rounds, and — the reason it
matters — **stateful defenses advance contiguously.** DeFL carries Beta reputation
counts and `S(t-1)` across rounds and DnC carries a subsampling RNG; under a random
rotation an algorithm's memory advanced on ~1 round in 4, scattered. Here it
advances over 10 consecutive rounds, much closer to how it behaves deployed alone.

- **INACTIVE under `defense.mode: llm`** (the default): there is no algorithm axis,
  and the attack strength is the ladder's, not a schedule's. Logged at startup.
- **The block is fixed for the whole round**, so it applies to the clean
  counterfactual and the commit alike.
- **The FL interlude between phases does not consume a slot** — it is not a GRPO
  training round.
- **Resume-safe.** The whole position is one integer, checkpointed in
  `checkpoints/rl_progress.json`, so a restart continues mid-block.
- Knobs: `rounds_per_block` (10), `algorithms` (`null` = `defense.algorithms`, in
  listed order — set a list to narrow or reorder the sweep). `enabled: false`
  restores the random draw.

Each round log records its block in `attack_metadata.curriculum`.

## Why GRPO (not PPO / DPO)

The reward is an exactly-computable scalar per round (RLVR regime). **DPO** is
offline/preference-pair based and discards reward magnitude. **PPO** needs a
learned value/critic network whose per-token credit assignment buys nothing for a
single terminal-reward emission. **GRPO** is critic-free: sample `G` completions
per state and use the group-normalized reward as the advantage. The reward is
deliberately **continuous** (a confidence-weighted soft F1, not a hard hit/miss) so
the within-group spread — and thus the gradient — doesn't collapse.

Note that all `G` rollouts classify the **same** cohort of updates, so the only
source of within-group spread is the defender's own sampling temperature
(`rl.temperature`, default 1.0). At temperature 0 every rollout is identical, the
advantages collapse, and no step is ever taken.

## LLM handling (read before training)

- **Training happens on a GPU machine — not through Ollama.** Ollama and the
  OpenAI API are **inference-only** and cannot fine-tune.
- The policy is **one frozen `Qwen2.5-3B-Instruct` base loaded via Unsloth in
  bf16 LoRA by default** (4-bit QLoRA is available via `rl.load_in_4bit: true` —
  use it only when GPU memory is tight; on a 5090 bf16 is faster as it skips the
  per-matmul dequant), with **one LoRA adapter** over it: `defender`. The base is
  never duplicated; the policy is a small adapter saved to
  `checkpoints/defender_adapter/`. (Loaded with `attn_implementation="eager"` by
  default — see `rl.attn_implementation`; Qwen2.5 also supports `"sdpa"`.)
- GRPO is implemented directly in [`rl/grpo.py`](rl/grpo.py) (environment-coupled
  reward, KL penalty to the frozen base) on top of Unsloth + PEFT — no TRL trainer
  dependency required.
- **Resume**: rerun the same command. The existing adapter and
  `checkpoints/rl_progress.json` are reloaded and training continues where it left
  off — the trained adapter, the round count (`rounds_done`), the FL round number
  (`round_index`), the phase schedule (`controller`), the curriculum position, and
  **the label-flip ladder's level and cycle** (`attacker`). Resuming the ladder
  matters: without it a restart would rewind the attack to full poison and replay
  strengths the defender is already past, making the schedule depend on how often
  the run happened to crash. Old progress files missing any of these still load.
- **Switching the base model invalidates old adapters.** A LoRA adapter is
  dimensioned for the exact base it was trained on. If `checkpoints/defender_adapter/`
  exists from an old base, delete it (and `checkpoints/rl_progress.json` +
  `checkpoints/fl_state.pt`) and retrain. The Phase-1 MNIST checkpoint
  (`global_model.pt`, `client_updates.pt`, `baseline.json`) is model-agnostic and
  can stay.
- **`gpt-4o-mini` (OpenAI) and Ollama `qwen2.5` are inference/baseline only** —
  used by `--dry-run`. They are **not** fine-tuned.
- **Serving a trained adapter**: use **vLLM** (multi-LoRA hot-swap), or **merge**
  the adapter into the base and export a single GGUF for Ollama.
- **Hardware**: Qwen2.5-3B fits comfortably on a single GPU — ~6 GB of weights in
  the default bf16 LoRA (or ~2–3 GB floor under 4-bit QLoRA). Generation is short:
  the defender emits one verdict per client (20 clients), and `rl.max_new_tokens`
  defaults to 1536 to fit the full verdict list without truncation. A verdict cut
  off mid-JSON parses as nothing, and every client then defaults to benign.

## Usage

```bash
# Full GRPO training (GPU). Phase 1 runs once, then the defender-learning rounds.
python main.py --env linux

# Quick smoke run: few rounds. --rounds is an ABSOLUTE budget overriding
# fl.simulation_rounds, so on a resumed run the rounds already done count toward it.
python main.py --env linux --rounds 8

# Run against a different config file
python main.py --env linux --config configs/my_experiment.yaml

# Verbose DEBUG run (GPU) — print EVERYTHING for one short run, to the console AND
# logs/debug.json: the round's label-flip plan (level + per-client flip counts),
# every client's local training, the exact defender prompt + raw outputs + parsed
# verdicts, all rewards / GRPO advantages, the commit, and where the ladder moved.
# Third-party library noise is silenced. Without --rounds it runs 3 MORE rounds
# than are already done, so debugging a resumed run still executes rounds.
python main.py --env linux --debug
python main.py --env linux --debug --rounds 6     # debug a longer stretch

# Logic dry-run — full round loop with a FROZEN defender LLM via Ollama (no training)
python main.py --env linux --dry-run --rounds 4

# Plumbing sanity — NO LLM at all: the label-flip ladder vs a fixed heuristic
# defense. Two things should be visible in a few CPU-seconds: the attack does
# measurable damage, and the printed flip_fraction walks down, hits the floor and
# resets (the saw-tooth the whole design rests on).
python main.py --baseline --rounds 20

# Force fresh Phase-1 training
python main.py --env linux --fresh

# Visualize results
python visualize_rounds.py

# MONITOR training health
python monitor.py                 # prints a health report + saves logs/monitor/health.png
python monitor.py --window 50     # smooth over a larger recent window for long runs
```

## Run inference on the trained defender

```bash
# Real system prompt it was trained with, feature JSON as the user message:
python infer.py --role --prompt '{"client_ids":[0,1,2,3,4],"features":{}}'

# Sample several completions (temperature > 0):
python infer.py --role --prompt '...' --n 4 --temperature 1.0

# Interactive — load the 3B model ONCE, then keep prompting (best for exploring):
python infer.py --role --interactive

# Pipe a prompt from stdin / a file:
cat my_features.json | python infer.py --role

# Free-form prompt, no system prompt at all:
python infer.py --prompt "What statistics distinguish a label-flipped update?"
```

There is no attacker adapter to run inference on — the attack is a deterministic
schedule, not a model.

Tune everything (which clients flip labels, the ladder's start/step/floor, GRPO
group size `G`, KL, learning rate) in [`configs/base.yaml`](configs/base.yaml).

## Configuration

- **`configs/base.yaml` → `fl:`** — FL hyperparameters (`n_clients: 20`,
  `poison_seed`, `local_epochs`, `client_data_refresh`, `client_round_fraction`,
  `freeze_global_in_phase2`).
- **`configs/base.yaml` → `attack:`** — **the attack**. `type` (`label_flip`, the
  only implemented one — an unrecognised value is a config error, not a request for
  a different attack), `poison_client_ids` (which clients flip labels), and
  `schedule` (`start_fraction`, `step_fraction`, `floor_fraction`, `caught_rule`).
  Plus `goal` — the **damage bar** the round is reported against, which does *not*
  change what the attack does.
- **`configs/base.yaml` → `defense:`** — who defends. `mode` (`llm`, the shipped
  default, vs `algorithmic`), the `algorithms` rotation pool, `selection`
  (`random` / `round_robin`, ignored while the curriculum is on), the algorithm-draw
  `seed`, `assumed_byzantine` (DnC / Multi-Krum's assumed adversary budget), and
  each algorithm's own knobs. See [Defense modes](#defense-modes).
- **`configs/base.yaml` → `curriculum:`** — the defense-algorithm sweep;
  `enabled`, `rounds_per_block`, `algorithms`. Inactive under `defense.mode: llm`.
- **`configs/base.yaml` → `rl:`** — GRPO + LoRA + the phase schedule + the
  defender reward, and `league_max_snapshots` (the ring-buffer cap on retained
  checkpoints — each costs ~115 MB of host RAM, so leaving it unbounded OOMs a long
  run).
- **`configs/defender_agent.yaml`** — defender-LLM defaults (`default_confidence`,
  `emit_reason`).

### The ladder's knobs

| Setting | Default | Controls |
|---|---|---|
| `attack.poison_client_ids` | `[0]` | which clients flip labels, every round |
| `attack.schedule.start_fraction` | `1.0` | the top of the ladder — where each cycle begins |
| `attack.schedule.step_fraction` | `0.1` | how far one detection backs the attack off |
| `attack.schedule.floor_fraction` | `0.5` | the bottom; caught here resets instead of descending |
| `attack.schedule.caught_rule` | `all` | with several poisoned clients, how many must be flagged to step down (`all` / `majority` / `any`) |

A floor that is not on the step grid is snapped **up** to the nearest reachable
level (with a log line), so the ladder can never descend past what you configured.
Ids outside `0..n_clients-1` are dropped with a warning rather than clamped —
clamping `[0, 25]` would silently produce two attacks on whichever id the clamp
landed on.

Note that once `len(poison_client_ids)` reaches half of `fl.n_clients` the
federation has no honest majority, and the robust aggregators (Multi-Krum, DnC,
FLTrust's trust scores) are outside the regime they are proved in. That is a
legitimate experiment — it is the standard "attack success vs fraction malicious"
sweep — it just has to be read with the caveat. It is logged at startup.

### The damage bar

`attack.goal.target_accuracy_drop: 0.10` sets the scale the round's measured drop
is **reported** against: `attack_effectiveness` is 1.0 when the round cost the
model 10 accuracy points. `rl.win_fraction` (0.6) then defines the recorded
`attack_damaging` / `attack_success` metric — did this round's flipped labels
actually cost something, i.e. a 0.06 drop here.

Nothing is trained on either, because the attack has no policy. They exist so a
run can answer a question the defender's own reward cannot: *was the thing I got
good at catching actually an attack?* A run where the defender wins every round
but `induced_drop` sits at zero is a defender that learned to detect a formality.

Attack goals: `untargeted_degrade` (target accuracy drop), `slow_degrade`
(per-round drop), `targeted_label` (per-class — scaffolded; currently falls back to
overall accuracy).

`attack.sample_target_in_training: true` re-draws the target per round from
`attack.target_choices`. It is off, because a bar that moves round-to-round makes
`attack_effectiveness` incomparable between rounds for no gain.

A round whose defense produced no clean aggregate has **no** counterfactual to
measure. Those rounds are marked `clean_measured: false` in the round log and are
excluded from the damage statistics; a round whose defense rejected the honest
majority of the *unpoisoned* cohort is marked `defense_sane: false` and likewise
excluded. Both are readings of the defense, not of the attack.

## Benchmark

Measure a panel of defenses against the same attack:

```bash
python -m benchmark.run_benchmark --rounds 200

# Pin the attack at one strength for a clean per-defense comparison:
python -m benchmark.run_benchmark --rounds 200 --flip-fraction 1.0

# The standard "attack success vs fraction malicious" sweep:
python -m benchmark.run_benchmark --rounds 200 --poison-clients 0,1,2,3,4

# Choose which defense's verdicts drive the ladder ('none' holds it at the start level):
python -m benchmark.run_benchmark --rounds 200 --ladder-feedback fltrust
```

Every defense sees byte-identical updates each round (the env builds the cohort
once), so only the defense varies. The `llm_defender` column needs a trained
defender adapter; without one it is dropped with a warning rather than aborting
the run. No attacker model is needed at all.
